# 业务规则

这份是动手写代码之前先定的一版规则。写的过程中有几处改了做法、有几处发现规则本身没写全，都在下面用「本仓库」标出来。每条规则的推导过程和实测数字不在这儿，在对应的代码注释里，这份只记规则本身。

## 数据来源

### REAL_PUBLIC

NYC OpenData 的 AMPS 数据集导入进来的五张表：

| 表 | 行数 |
| --- | ---: |
| `assets` | 148,423 |
| `work_orders` | 2,220,853 |
| `work_order_labor` | 3,202,020 |
| `transactions` | 752,746 |
| `transaction_details` | 2,290,091 |

原始文件不可修改，所有转换结果必须能追溯回 `source_record_id`。

### SYNTHETIC_PLATFORM

平台用户自己建的：工单、状态历史、处理记录、用户、角色、权限、操作日志。平台工单可以挂在真实资产上，但不会把平台状态写回 AMPS 的原始工单。

### 一条容易被默认值坑掉的规矩

`data_source` 这一列在模型上带着默认值 `REAL_PUBLIC`。写接口要是忘了显式指定，数据库会默默把平台自己录的记录标成官方数据 —— 那条记录从此谁都改不动，而且全程不报错。所以每个写接口都必须把目标数据源写出来，不许指望默认值。

## 工单状态机

| 当前状态 | 能去哪些状态 |
| --- | --- |
| `PENDING` | `ASSIGNED`、`REJECTED` |
| `ASSIGNED` | `IN_PROGRESS`、`REJECTED` |
| `IN_PROGRESS` | `COMPLETED` |
| `COMPLETED` | `CLOSED` |
| `REJECTED` | 终态 |
| `CLOSED` | 终态 |

补充规则：

- `PENDING -> ASSIGNED` 必须走分派接口，不能拿改状态的方式绕过去
- 分派的目标用户必须处于启用状态，而且要有 `ENGINEER` 角色
- 工程师只能操作分配给自己的工单
- 工程师只能执行开始处理和完成
- 驳回必须填原因
- 完成时写入平台自己的 `completion_date`

### 本仓库怎么落的

「工程师只能操作分配给自己的工单」和「工程师只能执行开始和完成」是两件事，分别管「哪张单」和「哪个动作」，两条都判了 —— 少判前一条，工程师能把别人手上的单点成已完成；少判后一条，工程师能自己把单关掉。「必须走分派接口」落在分派那个方法里。

判断顺序是三道闸门：先看数据源（官方导入的不许动），再看状态机（这一步合不合法），最后看人（这个动作归不归你）。

`COMPLETED` 不算终态，它后面还有一步 `CLOSED`。这一点特别容易搞错，因为「完成」两个字听起来就像结束了。

## 真实历史工单

`REAL_PUBLIC` 那 222 万单，业务接口不允许：

- 改描述
- 重新分派
- 改状态
- 加平台处理记录

允许拿它们做的：查询、资产维护统计、关联工时和交易、进 Dashboard 趋势。

这一条是那批数据的意义所在 —— 它代表已经发生过的事，谁改了都说不清。

### 一处刻意放松

工时的写接口不检查工单的数据源，也就是说允许往历史工单上记工时。这不是漏了：规则里「真实历史工单可以用于」那一节明确列了「Labor 和 Transactions 关联」，给历史单记工时正是它允许的用法。真正不许动的是改历史单本身。

另一处放松：录工时也不检查「这张单是不是派给我的」。理由是历史工单根本没有归属信息（AMPS 里没有这一列，导入时也没映射），加上这道闸门会让工程师永远给历史单记不了工时 —— 功能直接不可用。

## 源状态映射

Work Orders 的原始数据里没有独立的状态列，工作流值藏在 `EVT_UDFCHAR13` 里。入库时按一张映射表标准化：

| 源状态 | 标准化状态 |
| --- | --- |
| `Completed`、`GT Completed` | `COMPLETED` |
| `Cancelled`、`Rejected`、`Duplicate/Rejected` | `REJECTED` |
| `Open`、`Returned`、`Awaiting Release`、`Work Request`、`Part Added` | `PENDING` |
| 没认出来的值 | 原样保留 |

三个字段分工：`source_status` 留原值，`status` 存标准化值，`status_origin` 记这个状态是怎么来的（官方数据的都是 `DERIVED_FROM_SOURCE`，只有平台自己流转过才不是）。

另几个原始字段保留原样，不代表平台的优先级或 SLA：`EVT_UDFCHAR06` 进 `assigned_title`，`EVT_UDFCHAR01` 进 `source_priority`，`EVT_UDFCHAR05` 进 `source_notes`。

## SLA

AMPS 里没有 SLA 这个概念，这几条是平台自己定的（规则里管它叫 Synthetic Platform Business Rule）：

| 优先级 | 目标处理时间 |
| --- | ---: |
| `P1` | 30 分钟 |
| `P2` | 2 小时 |
| `P3` | 8 小时 |
| `P4` | 24 小时 |

平台工单落三列：`priority`（人录单时选的）、`sla_deadline`（建单那一刻起算）、`sla_source = PLATFORM_RULE`。历史工单这几列全是 NULL —— 不去给它们伪造一个。

起算点用「建单那一刻」而不是 `request_date`，因为那一列是个 `date`、没有时分秒，拿它加 30 分钟等于当天零点就已经逾期，P1 的单一建出来就该报警，那这个字段就白算了。

库里还有一个 `sla_policy` 列，故意不写：`created_at` 和 `sla_deadline` 一减就是当时用的时限，一眼看得出来的东西不用再存一份加工版。真存了的话，规则哪天改了、老数据又没重算，就会跟 deadline 对不上。

### 没做的那部分

规则里列了五种 SLA 状态：`NORMAL` / `DUE_SOON` / `OVERDUE` / `COMPLETED` / `NOT_APPLICABLE`，但一条判定条件都没给 —— 尤其 `DUE_SOON` 是提前多久算「快到了」，从头到尾没有定义。没有阈值的状态机没法实现，硬编一个等于自己发明业务规则，所以这一版只存 `sla_deadline`，SLA 状态没做。

## RBAC

| 角色 | 资产 | 工单 | 分派 | 流转 | 工时 | 交易 | 统计 | 系统管理 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `ADMIN` | 读 | 读写 | 是 | 是 | 读写 | 读 | 是 | 是 |
| `DISPATCHER` | 读 | 创建/改 | 是 | 是 | 读 | 读 | 是 | 否 |
| `ENGINEER` | 读 | 查看 | 否 | 本人工单 | 创建/读 | 读 | Dashboard | 否 |
| `VIEWER` | 读 | 读 | 否 | 否 | 读 | 读 | 是 | 否 |

实现方式是 13 个权限点（写成 `资源:动作`）+ 每个角色挂一组。真正校验在后端，前端隐藏菜单不算授权（这一版还没有前端）。

### 几处对不上的地方

「工单」那列写 `DISPATCHER` 是「创建/改」、`ENGINEER` 是「查看」，但正文里又说工程师能开始和完成。表格和正文说的不是一回事：表格那张管的是能不能碰工单这一行，正文那句管的是能碰的人里哪个动作归谁。两层都要过，缺一层就是漏洞 —— 落库时这两层是分开实现的。

规格里 `ENGINEER` 的「统计」写的是 `Dashboard`、`VIEWER` 写的是「是」，看着像有区别。落库时这两个角色都给 `dashboard:read`，也就是四个角色都能看这一页，只是叫法不同。

有两个权限点在库里存在，但这一版没有对应的接口：`analytics:read`（`ADMIN` / `DISPATCHER` / `VIEWER` 有）和 `operation_log:read`（只有 `ADMIN`）。前者对应的 `/analytics/overview` 没做，后者对应的 `/operation-logs` 没做。

## 操作日志

至少记这些：登录成功、登录失败、用户停用、角色修改、建工单、分派、改状态、加处理记录。

本仓库实际还多记了一条：创建工时。那张表是下限不是上限，写操作留痕是贯穿全项目的做法，建工时漏掉的话「这条工时是谁记的」事后就查不到了。

驳回原因只写工单流水、不写操作日志。操作日志管的是「谁在什么时候做了什么」，驳回原因是工单自己的业务数据；两处都存的话，将来只改一处就会不一致，而这两张表的一致性没人会去查。

## 空值不伪造

原始数据里的空值不许用推测值补上。落到代码上有几处：

- 工时合计的两个 `SUM` 允许是 `None`。空表上 `SUM` 返回 NULL 不是 0，而且「合计 0 小时」读起来像「确实有人干活但没花时间」，跟「一条记录都没有」是两回事
- 外键解析不了的保留 NULL，记进导入报告，不去猜一个
- 官方主键重复时按源更新次数保留最新版本，并记录去重数量

## Dashboard

- 数字全部来自数据库聚合，不写死
- 没有官方字段支撑的图表不做（比如区域分布 —— AMPS 快照里没有可靠的区域字段）
- 平均处理时长取最近 12 个月
- 真实数据和平台数据靠 `data_source` 区分

「活干完了没有」分成三个桶：未完结（`PENDING` / `ASSIGNED` / `IN_PROGRESS`）、已完成（`COMPLETED` / `CLOSED`）、已退回（`REJECTED`）。

这个分组规则里没有。规则只给了上面那张「源状态 -> 标准化状态」的映射表，从头到尾没提过哪些状态算未完结。所以这三个桶是自己切的，依据就是状态机本身：主干一刀切在 `COMPLETED` 上，`REJECTED` 是条死胡同、单独占一个桶。不留这个桶的话，「总数 / 未完结 / 已完成」三个数对不上账，看的人只会以为数字算错了。

## 还悬着的几个问题

这几条是规则没给全、这一版就没硬做的，记下来免得以后以为是漏了：

| 问题 | 缺什么 |
| --- | --- |
| SLA 状态 | 五种状态没有判定阈值，`DUE_SOON` 到底提前多久 |
| 工时里的编码 | `trade`（97 种）、`operation_type`（2 种）没有码表，只能卡长度不能校验取值 |
| 交易里的编码 | `action`（19 种）、`transaction_type`（6 种）同上 |
| 交易的目标 | `to_entity + to_code` 是多态的，目标可能是工单也可能是仓库，其他目标怎么展示没定 |
